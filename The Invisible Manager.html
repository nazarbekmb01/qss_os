A CPU executes about 2 × 10⁹ instructions per second. Input and output devices are much, much slower. Look at what that means on a human scale.

If one CPU instruction took 1 second…

Screen 50 MB/s · 1 byte = 2×10⁻⁸ s
40 seconds
Disk 5 MB/s · 1 byte = 2×10⁻⁷ s
≈ 7 minutes
Keyboard 10 B/s · 1 key = 0.1 s
≈ 6 years

Bars are not to scale: the keyboard bar would be 5 million times longer than the screen bar.

Your turnHow many instructions could the CPU execute while you press ONE key? Write the calculation in your notes. (Hint: time × speed.)

The OS toolkit

Read the six cards. Each one is a way the OS keeps resources busy. You will need them for your poster.

CPU

Multiprogramming

Several processes are kept in memory at the same time, so the CPU always has another job ready.

Music keeps playing while you type an essay.

CPU

Scheduling

The scheduler decides which ready process gets the CPU next and for how long (a time slice of a few milliseconds).

280 processes take turns so fast that it looks like they all run at once.

CPU + I/O

Interrupts

A device sends a signal when it has finished. The CPU does not have to keep asking "are you ready?" (that is called polling).

An oven timer: the cook does other work until it rings.

I/O

Buffering

Data is collected in an area of memory called a buffer, so it moves in blocks instead of one byte at a time.

YouTube loads the next seconds of video before you watch them.

I/O

Spooling and DMA

Spooling: slow jobs (printing) wait in a queue on disk. DMA: a controller copies a block between a device and memory without the CPU, then sends one interrupt.

30 students print at once; a 5 GB file is copied to a USB stick.

Memory

Memory management

The OS decides which processes are in RAM and where, protects each process's memory, and frees memory when a process ends. More ready processes means more choice for the scheduler.

40 browser tabs open; one tab crashes, the others survive.

In Harvard's CS50, David Malan calls abstraction one of the most important ideas in computer science: hide the details so people can think about the big picture. The OS is a stack of abstractions between you and the hardware.

What really happens when you press "Save"?

Tap the steps in the order they happen, from your click down to the hardware.

Your order will appear here.

CountWhen the correct order is shown, count the steps the user sees. How many does the OS hide?

The same idea in code

Run these three lines in Python. Then find hello.txt in your folder.

with open("hello.txt", "w") as f:   # API call → system call → kernel
    f.write("Hello, OS!")            # kernel → file system → driver → disk
print("Saved!")

open() and write() are part of an API: ready-made requests. Inside, Python makes a system call to the OS kernel. Your code doesn't know whether the disk is an SSD, a hard drive or a USB stick, which sector to use, or which driver to call.

TryChange the path so the file is saved somewhere else (another folder or a USB stick). What else did you have to change in the code? Why?

Why programs can't touch the hardware

UserClicks, taps, types, speaks
User interfaceGUI, command line or voice
ApplicationsRun in user mode: no direct access to hardware
── system call: the only door ──
KernelRuns in kernel mode: full control of hardware
Device driversTranslate OS commands for one specific device
HardwareCPU, memory, disk, printer, screen

It's like a restaurant: you order from the menu, but you never walk into the kitchen. If one program crashes or is malicious, it can't damage the others or read their data.

Four ways the OS hides complexity

For the user

User interface

GUI, command line or voice. You use icons, menus and words instead of machine instructions.

"Hey Siri, set a timer."

For the user

File system

You see file names and folders. The OS maps them to physical blocks on the disk.

Homework/essay.docx, not "sector 48 213".

For devices

Device drivers

Each device understands its own commands. The driver translates, so the OS can treat every printer the same.

One "Print" button works for any printer.

For programmers

System calls and APIs

Programs ask the OS for a service instead of writing hardware code.

open() works on any drive.

Glossary: key terms
Resource
Anything processes need: CPU time, main memory, I/O devices, storage.
Multiprogramming
Several processes in memory at once, so the CPU always has work.
Scheduler
The part of the OS that chooses which process runs next.
Interrupt
A signal to the CPU that an event needs attention.
Buffer
Memory that holds data temporarily between devices of different speeds.
Spooling
Putting output jobs (e.g. printing) in a queue on disk.
DMA
Direct Memory Access: a controller moves data between a device and memory without the CPU.
Kernel
The core of the OS, always in memory, runs in kernel mode.
Device driver
Software that translates OS commands for one specific device.
API / system call
A ready-made request a program makes to use an OS service.
Abstraction
Hiding details so you can work with the big picture.
